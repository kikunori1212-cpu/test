# SECCON Beginners CTF 2026で学ぶリバースエンジニアリング入門

## baby-rev / old-virus Writeup

SECCON Beginners CTF 2026のReversingカテゴリから、`baby-rev`と`old-virus`の2問を解きました。

この2問は難易度こそ異なりますが、共通して重要なのは、プログラムを闇雲に動かすことではなく、手元にある情報から処理を小さく分解することでした。

本記事ではflagそのものよりも、以下を中心に整理します。

- 問題が何を試していたのか
- どこで判断を誤りやすいのか
- 解くために必要だった技術
- 実務のセキュリティ調査へどう応用できるか

> この記事には問題の解法とflagを含むネタバレがあります。

## 1. baby-rev

### 問題の概要

`baby-rev`は、C言語で書かれた入力検証プログラムを読み、正しい入力を復元する問題です。

プログラムには、暗号化された34バイトの配列と固定値`0x88`が格納されていました。入力された各文字について、次の比較が行われます。

```c
if ((inp[i] ^ xorKey) != xorFlag[i]) {
    printf("Wrong:(\n");
    return -1;
}
```

ここで`xorKey`は`0x88`です。

### 問題の特性

この問題のテーマは、XORの可逆性です。

プログラムが確認している条件は、次の式で表せます。

```text
入力値 XOR 0x88 = 格納された値
```

XORは同じ値をもう一度適用すると元に戻ります。

```text
(A XOR K) XOR K = A
```

したがって、求める入力値は次の式で復元できます。

```text
入力値 = 格納された値 XOR 0x88
```

Pythonでは以下のように書けます。

```python
flag = bytes(value ^ 0x88 for value in xor_flag)
print(flag.decode("ascii"))
```

復元結果は次の通りです。

```text
ctf4b{l00k_m0m_n0_h4nds_just_x0r!}
```

### ひっかかりやすい箇所

#### 「暗号」と聞いて難しく考えすぎる

16進数の配列を見ると、複雑な暗号処理を想像しがちです。しかし、実際の比較処理は固定値とのXORだけでした。

先にアルゴリズム名を推測するより、比較式をそのまま数式として読む方が早く解けます。

#### デバッガやGhidraをすぐ使おうとする

リバースエンジニアリングではGhidraやデバッガが有効ですが、今回のようにソースコードが与えられている場合は不要です。

高度なツールを使うこと自体が目的になると、単純な処理を見落とします。まず入力がどのように変換され、何と比較されているかを確認することが重要です。

#### 入力長の検査を見落とす

このプログラムは内容だけでなく、入力が34バイトであることも検査しています。復元した文字列が正しくても、改行や空白を含めると検証に失敗する可能性があります。

CTFでは、値だけでなく長さ、文字コード、終端文字も確認対象です。

### 解くために必要な技術力

- C言語の配列、ループ、条件分岐を読める
- 16進数とバイト列の関係を理解している
- XORの基本性質を理解している
- 数十行程度のPythonスクリプトを書ける
- 入力長や文字コードも検証条件として確認できる

この問題で問われたのは、高度な逆アセンブル能力ではありません。短いコードから本質的な処理だけを抜き出す読解力です。

## 2. old-virus

### 問題の概要

`old-virus`は、2000年代風のランサムウェアを模したELFバイナリと、暗号化された`flag.txt.hacked`を解析する問題です。

問題文では実害のないプログラムであることが明記されています。しかし、未知の実行ファイルを扱う以上、最初から実行するのではなく、静的解析から始めました。

最初に使用したコマンドは次の通りです。

```bash
file old-virus
strings -a -n 4 old-virus
readelf -h -S -s old-virus
objdump -d -Mintel old-virus
```

### 問題の特性

この問題は、暗号アルゴリズムを破る問題ではありません。

バイナリから次の情報を回収し、暗号化処理を逆順に再現する問題です。

- 使用されている暗号方式
- 暗号化の順序
- 埋め込まれた鍵
- padding方式

`strings`とシンボル情報から、以下が判明しました。

- AES-128-ECBを使用
- RC4を使用
- `aes_ecb_encrypt`と`rc4`という関数名が残っている
- AES鍵とRC4鍵が`.rodata`に平文で格納されている

抽出できた鍵は次の通りです。

```python
AES_KEY = b"THISISNOTAESKEY!"
RC4_KEY = b"ImashyKey!Dontlookme!!!"
```

逆アセンブルから、元データに対して以下の順番で処理していることを確認しました。

```text
平文
  ↓ PKCS#7 padding
AES-128-ECB
  ↓
RC4
  ↓
flag.txt.hacked
```

復号では処理を逆順に適用します。

```text
flag.txt.hacked
  ↓
RC4復号
  ↓
AES-128-ECB復号
  ↓ PKCS#7 unpad
平文
```

Pythonによる復号処理は次のようになります。

```python
from Crypto.Cipher import AES, ARC4
from Crypto.Util.Padding import unpad

aes_ciphertext = ARC4.new(RC4_KEY).decrypt(encrypted)
padded = AES.new(AES_KEY, AES.MODE_ECB).decrypt(aes_ciphertext)
plaintext = unpad(padded, AES.block_size)
print(plaintext.decode("ascii").strip())
```

復元結果は次の通りです。

```text
ctf4b{Y2K_n05t419ic_viru5_6ut_G2G}
```

### ひっかかりやすい箇所

#### 問題文を信用してすぐ実行する

今回は安全な疑似マルウェアですが、解析の基本姿勢として、未知の実行ファイルをホストOS上で即座に実行するべきではありません。

まずハッシュを取得し、ファイル形式、文字列、シンボル、インポート関数を確認します。動的解析が必要な場合も、隔離した仮想環境やコンテナを利用するのが原則です。

#### 「hard」なので暗号解読が必要だと思い込む

AESやRC4が登場しますが、暗号方式そのものを攻撃する必要はありません。鍵がバイナリ内に平文で埋め込まれているためです。

難易度表示に引っ張られず、まず以下を確認する方が効率的です。

- バイナリがstripされているか
- 関数名が残っているか
- 暗号ライブラリのインポートがあるか
- `.rodata`に鍵らしい文字列がないか

#### 暗号化と同じ順番で復号してしまう

複数の変換を重ねた場合、復号は逆順です。

```text
暗号化: AES → RC4
復号:   RC4 → AES
```

この順番を間違えると、各アルゴリズムの使い方が正しくても平文には戻りません。

#### paddingを処理し忘れる

AES復号後のデータにはPKCS#7 paddingが残ります。復号結果の末尾に同じ値が複数並んでいる場合、文字化けではなくpaddingの可能性があります。

今回も、AES復号後に`unpad`を適用する必要がありました。

#### `strings`だけで結論を出す

文字列から鍵の候補は見つかりますが、どちらがAES鍵でどちらがRC4鍵か、暗号化順序はどうなっているかまでは断定できません。

`strings`は仮説を作る道具です。最終的にはシンボル、引数、呼び出し順序を逆アセンブルで確認する必要があります。

### 解くために必要な技術力

- ELFバイナリの基本構造を理解している
- `file`、`strings`、`readelf`、`objdump`を使える
- `.rodata`、シンボルテーブル、インポート関数を確認できる
- 関数呼び出しから処理順序を復元できる
- AES、ECB、RC4、PKCS#7 paddingの役割を理解している
- PyCryptodomeを使って検証コードを書ける
- 未知のバイナリを安全に扱う判断ができる

Ghidraを使っても解けますが、この問題ではコマンドラインの静的解析だけでも十分な情報を得られました。

## 2問を比較して見えたこと

| 観点 | baby-rev | old-virus |
|---|---|---|
| 主な対象 | Cソースコード | x86-64 ELFバイナリ |
| 中心技術 | XORの逆算 | 静的解析と多段復号 |
| 最初に見る場所 | 比較条件 | 形式、文字列、シンボル |
| 必要なツール | Python | file、strings、readelf、objdump、Python |
| 典型的な罠 | 難しく考えすぎる | 実行してしまう、復号順を誤る |
| 実務との接点 | 認証・検証ロジックの読解 | 不審ファイル調査、暗号実装レビュー |

両方に共通するのは、「観察した事実」と「推測」を分けることです。

例えば`old-virus`では、文字列にAES鍵らしい値が見つかった段階ではまだ仮説です。関数名、鍵長、暗号ライブラリ、呼び出し順序が一致して初めて、復号手順として確定できます。

## 業務へ応用できる学び

### 1. 未知ファイルは実行前に情報を取る

不審ファイル調査では、実行前にハッシュ、形式、文字列、インポート、署名、メタデータを取得します。これはインシデント対応やマルウェア一次解析でも同じです。

### 2. 複雑な処理を変換単位に分ける

「暗号化されたファイル」と一括りにせず、padding、AES、RC4という処理単位に分けることで、逆変換の順序が明確になります。

### 3. 固定鍵の埋め込みは秘密管理にならない

クライアントアプリや実行ファイルに鍵を埋め込んでも、利用者がバイナリを取得できるなら回収される可能性があります。

実務では、鍵をコードやバイナリへ直接埋め込まず、用途に応じてKMS、HSM、Secret Manager、OSの資格情報保管機能などを使用する必要があります。

### 4. 小さな検証コードで仮説を確かめる

解析結果を頭の中だけで完結させず、短いPythonコードで復元できるか確認しました。

検証コードには次の価値があります。

- 手順の再現性を確保できる
- 処理順序や鍵の認識ミスを発見できる
- 他の担当者へ根拠を共有できる
- writeupや報告書の証跡になる

## まとめ

`baby-rev`は、短い比較処理からXORの逆算を見抜く問題でした。

`old-virus`は、疑似ランサムウェアを安全に静的解析し、バイナリ内の鍵と暗号化順序を特定して復号する問題でした。

難易度や派手な演出に引っ張られず、次の順序で調べることが重要です。

1. 入力と出力を確認する
2. 変換処理を小さく分解する
3. 定数、鍵、比較条件を探す
4. 処理の順序を確認する
5. 最小限のコードで仮説を再現する

リバースエンジニアリングは、アセンブリを大量に読むことだけではありません。観察できる情報を整理し、プログラムが行った処理を逆向きに組み立て直す技術です。
